## Context

`packages/compiler/src/Stdlib.ts` currently authors `silk/vector` inside a JavaScript template string and exposes only a module-to-byte map. Module analysis receives exact bytes but not a truthful physical origin. The LSP therefore maps every canonical module identity below the project root, producing a nonexistent URI for standard-library declarations.

## Goals / Non-Goals

**Goals:**

- Make physical `.silk` files the only editable stdlib source of truth.
- Preserve deterministic in-memory loading for browser/tooling consumers.
- Carry enough source-origin data for truthful diagnostics and navigation.
- Ship and verify the source files in packed compiler artifacts.

**Non-Goals:**

- Change `silk/vector` semantics or spelling.
- Add a public package manager, user-selectable stdlib, virtual editor documents, or runtime actors.
- Add `Option`, new primitive types, String, logging, or streams.

## Decisions

### Canonical source lives under packages/compiler/stdlib

Use `packages/compiler/stdlib/<module>.silk`, beginning with `silk/vector.silk`, plus a deterministic manifest ordered by canonical module identity. This mirrors the module path and gives repository, installed package, diagnostics, and editor tooling one source identity.

_Alternative considered:_ retain JavaScript strings and expose virtual documents. Rejected because virtual identities leave package contents and editor navigation disconnected from the ordinary source users should read.

### Generated embedding is derived and verified

Browser-compatible byte tables remain allowed, but a build script generates them from the manifest and canonical files. Tests compare generated bytes to disk exactly. The generated TypeScript artifact is not hand-edited.

_Alternative considered:_ read files synchronously at compiler runtime everywhere. Rejected because browser builds and single-artifact consumers still need embedded bytes.

### Source resolution returns origin alongside bytes

Extend successful resolved source data to include exact bytes and a discriminated origin: project file, toolchain file, or supplied in-memory source. Module closure keeps using canonical module identity for semantics while snapshots retain origin for diagnostics and tooling. Reserved `silk/` identities consult the stdlib manifest before project lookup.

_Alternative considered:_ teach only the LSP about stdlib installation paths. Rejected because it would reconstruct a location independently from the source bytes actually analyzed.

### LSP URI selection consumes analyzed origin

Navigation uses the target source's retained origin. File-backed stdlib targets return their toolchain file URI; in-memory targets with no URI continue to have no navigable physical definition rather than receiving a fabricated path.

## Risks / Trade-offs

- [Package installation moves files] → Resolve the stdlib root relative to the installed compiler package and cover packed-tarball layout in release-candidate tests.
- [Generated bytes drift] → Make generation deterministic and fail tests/package validation on any mismatch.
- [Origin data spreads through APIs] → Keep origin owned by the source/resolution actor and thread the value already carried by analysis snapshots rather than adding parallel LSP state.
- [Existing in-memory tests become filesystem-coupled] → Preserve a manifest-backed in-memory resolver path with explicit non-file origin.

## Migration Plan

1. Add the canonical source tree and manifest with bytes identical to the current embedded module.
2. Add deterministic generation and drift tests, then switch `Stdlib.ts` to the generated table.
3. Extend source resolution and snapshots with origin data.
4. Update LSP navigation to consume target origin.
5. Include source files in package contents and verify the packed release candidate.

Rollback reverts the source tree, generated table, origin field, and package-content change together; there is no compatibility format to preserve.
