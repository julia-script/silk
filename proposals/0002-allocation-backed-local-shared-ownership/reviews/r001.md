## Scope and language coherence

### Findings

No material scope finding. Explicit allocation, dynamically counted local lifetime, callback-scoped
interior access, last-handle cleanup, and non-transferability are one coherent ownership model.
Separating access from lifetime would leave neither child proposal independently useful: the handle
would either own an inaccessible value or expose aliases without a safe access rule.

The split from SLP-0001 is justified. Shared local lifetime is independently useful for observer
registries, memo cells, and caches, while execution transfer and wake ordering can change without
changing `Shared<T>`. Parallel shared ownership remains a genuine later thesis because atomics,
transfer derivation, memory ordering, and data races are absent from the local actor.

The selected first-version tradeoff is coherent: deriving `Shared.with` from exclusive
`sharedWithMut` deliberately rejects nested reads. That is a visible restriction, but it is stated,
tested by the reentrancy matrix, and subtracts a reader-count state the driving cases do not need.

### Proposed split, if any

None.

## Examples and programmer model

### Findings

The driving and worked cases cover the important ownership transitions: construction failure,
allocation-free clone, all reentrant access combinations, affine movement through ordinary state
operations, callback-loan escape, explicit and failure-path cleanup, strong cycles, execution
retention, thread rejection, count overflow, and evaluator/native/Wasm parity.

The mental model is learnable: clone duplicates only a strong obligation; access is temporary;
dropping the final obligation cleans `T` and then releases storage. The proposal does not disguise
cycles, overflow, reentrancy, or allocation behind value-like syntax.

Two clarifications would improve the dossier without changing its direction:

1. State explicitly beside the reentrancy matrix that the strong-count state is independent of the
   access state. Cloning or dropping a non-last alias during access does not constitute nested value
   access.
2. Add an explicit trace for a typed failure after successful construction, showing local cleanup
   order when multiple handles inhabit different frames. The prose already selects the outcome.

### Missing or corrected cases

No missing case rises to a proposal blocker. The two clarifications above can be added during a
future editorial revision or translated directly into OpenSpec scenarios.

## Compiler privilege and realizability

### Findings

The compiler boundary is defensible. Existing `Allocation`, `RawBuffer<T>`, and `Slot<T>` remain
affine; ordinary source cannot safely manufacture independently owned aliases, attach one dynamic
last-drop obligation, or derive `&mut T` from a shared handle. One opaque core with clone, exclusive
callback access, and intrinsic cleanup supplies exactly those missing facts.

`sharedLayout` and `sharedFromAllocation` keep allocation policy in ordinary Silk. Collapsing them
into an allocating intrinsic would force the compiler boundary to know an Allocator provider,
OutOfMemoryError, or a hidden allocation policy. Exposing raw header operations would be smaller in
surface spelling but larger in unsafe power.

The callback result must not carry the invocation-local borrow. Current Silk already treats borrows
as lexical call parameters rather than storable owned values; OpenSpec still needs an explicit
scenario proving that generic `A`, an Effect, and a callable cannot smuggle the borrow out.

Last-handle cleanup is realizable through the opaque core's compiler-known cleanup path specialized
for `T`. The control block must retain enough allocation ownership or release metadata to reclaim the
exact allocation after `T` cleanup on every target.

### Smaller boundary, if any

None found. A borrowed `LocalCell<T>` does not solve dynamic lifetime; raw pointers lose provenance;
an allocating intrinsic absorbs source policy; a separate read intrinsic adds behavior the current
cases do not require.

## Synthesis

### Proposal-level blockers

None.

### Editorial improvements

- Explain count-state versus access-state independence adjacent to the reentrancy matrix.
- Add the multi-frame typed-failure cleanup trace as a compact worked case.
- State that `onConflict` observes an already-active access without changing that access state.

### OpenSpec realization questions

- Define target-neutral `sharedLayout<T>` overflow and alignment behavior and the exact validity
  preconditions checked by unsafe `sharedFromAllocation`.
- Specify control-block ownership of allocation release metadata and the order: clean `T`, then
  release storage.
- Prove count increment checks before mutation and last-drop decrement/cleanup parity across
  evaluator, native, and Wasm.
- Specify the invocation-local callback loan and diagnostics for direct return, Effect capture,
  callable capture, and generic-result escape.
- Add the non-transferable semantic fact now, even though a later parallel proposal supplies its
  first thread-boundary consumer.

### Reviewer disagreements

The scope lens considered separating shared lifetime from dynamic access. The programmer-model and
privilege lenses rejected the split because every useful driving case needs both and the selected
single exclusive access operation is already the subtractive version.

questions belong in OpenSpec if the direction is accepted.
