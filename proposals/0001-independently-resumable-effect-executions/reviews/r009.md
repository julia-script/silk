## Scope and language coherence

### Findings

#### S1 — The selected capability point has independently subtractable axes

Revision 25 names three guarantees together: deferred owner-selected first activation, task-specific
push readiness, and caller-funded recoverable fixed packaging. The smaller alternative changes all
three at once, even though each has an independent countermodel:

- Initial execution can exist without Wake for heterogeneous deferred tasks that never park.
- Owner-sweep relinquishment can preserve correctness without push readiness.
- Push readiness can use fatal runtime storage without changing its eligibility protocol.
- Caller-funded executable erasure is useful even when a body never parks.

Required revision: analyze those axes independently. Either split independently outcome-capable
theses or define the one selected execution-admission contract and give each retained guarantee its
own driving evidence. Do not claim logical inseparability or absolute minimality.

#### S2 — Static selection and purpose-bound runtime dispatch are conflated

The proposal says no unknown runtime dispatch survives specialization while also requiring hidden
invoke/drop metadata for erased bodies and callbacks. Static specialization selects the exact hidden
implementation and suspension mode, but a later `drive` still dispatches through that purpose-bound
metadata. The pay-for-use text should distinguish those facts.

### Proposed split, if any

The scope lens proposed affine executable erasure/Initial lifecycle, independently relinquishable
execution, task-targeted Wake parking, and caller-funded package policy as dependency-ordered
children. The dedicated simplification lens instead requested an independent-axis comparison and
evidence for the selected capability point. The revision may defend one boundary only by making
that cohesion and the independent tradeoffs explicit.

## Examples and programmer model

### Findings

#### E1 — Positive Detached examples capture loans instead of owners

`firstActivation` borrows `childMarker` in the child Effect, `coroutineBody` borrows `port`, and the
positive lexical example drops `owned` without an explicit move. Moving the Effect value later does
not retroactively turn its borrowed captures into owned captures.

Required correction: move each owner into the Effect body before borrowing it locally, for example
`let ownedMarker = move childMarker`, and use `drop move owned` in the direct positive case. Explain
that moving an Effect value is distinct from moving values into its environment.

#### E2 — Detached provider provenance lacks the decisive accepted/rejected pair

The proposal says an empty requirement row may still conceal a borrowed provider, but demonstrates
only a scalar lexical borrow. Add one Effect whose requirement is eliminated through a borrowed
provider and remains non-Detached, beside the accepted owned-provider form. The diagnostic must be
distinct from an unsatisfied requirement.

#### E3 — The Timer result has no explicit source owner capable of delivering the event

`prepareConcurrentTimer` moves the only Timer provider into the closed execution and returns only
that Execution. Wake is non-transferable, yet the claimed same-thread reactor turn has no retained
source handle outside the dormant execution. The observable result therefore assumes an ambient
runtime that the proposal otherwise rejects.

Required correction: construct a local Timer provider and external reactor/control handle over
source-owned state, return the reactor beside the Execution, and show the source driver performing
Initial drive, suspension retention, same-thread fire/poll, readiness observation, Eligible drive,
and `Success(42)`. Add destruction before fire as the nearby cancellation case.

### Missing or corrected cases

- Make the future Coroutine outcome depend on the observed Yielded/Done sequence rather than return
  a constant after ignoring three values.
- Rename “complete ordinary-source sufficiency witness” unless every declared store/inbox/driver
  operation is actually supplied as a standalone program.

## Compiler privilege and realizability

### Findings

#### C1 — Per-drive readiness erasure is unnecessary for every selected guarantee

Every driving owner publishes repeated readiness to the same destination for one Execution, but
Revision 25 supplies a fresh exact `once` callback and caller-funded readiness Allocation on every
drive. A smaller boundary binds one reusable detached readiness callback and its Allocation when the
Execution is constructed, then reuses them across parks. Dynamic retargeting can remain ordinary
source indirection through shared state.

This preserves deferred first activation, O(1) task-specific notification, caller-funded package
failure, late-Wake safety, and owner-neutrality while removing callback replacement and readiness
Allocation handoff from `drive`. The proposal needs a contrary driving case or should adopt the
attach-once model.

#### C2 — Separate drive outcome callbacks cannot share one affine owner state

An ordinary source owner may take one affine lease before `drive`, but cannot move that lease into
both `onComplete` and `onSuspend`. The current Shared witness works only by cloning separate handles
for both branches.

Smallest correction: either use one outcome callback and an ephemeral drive-outcome sum, or pass one
generic affine branch state into `drive` and transfer it to exactly one of the two branch callbacks.
The latter preserves callback-shaped outcomes without forcing source owners into shared allocation.

#### C3 — Event ownership must remain source-visible

A non-transferable Wake cannot be fired by an unstated worker or ambient loop. The compiler lens
independently reproduced E3 and required an explicit same-thread reactor/control handle or a narrower
target claim.

### Smaller boundary, if any

The dedicated simplification lens identified four independent reductions:

| Axis | Selected guarantee | Independent subtraction and exact loss |
| --- | --- | --- |
| First activation | owner may enqueue heterogeneous unstarted Effects | eager `start`; loses owner-selected first activation and never-driven cleanup |
| Readiness | one ready task identity is pushed | owner sweeps dormant tasks; loses O(1) selection and natural parallel notification shape |
| Readiness storage | preflighted caller-funded fixed package | runtime package with fatal exhaustion; loses recoverable admission, pooling, and accounting |
| Drive branch | callback-shaped completion/suspension | one outcome callback or one affine branch state; loses no capability |

The reviewer also showed that fatal readiness-package storage can be combined with Initial execution
and push Wake, and that eager start can be combined with push Wake and caller-funded storage. The
revision must not present the previous all-or-nothing owner-sweep bundle as the only subtraction.

## Synthesis

### Proposal-level blockers

1. The proposal does not independently justify the capability axes or adequately defend one SLP
   outcome for their selected combination.
2. Fresh per-drive readiness packaging is not minimal under the selected guarantees.
3. The two drive branch callbacks exclude owners with one affine branch resource.
4. Several positive Detached examples do not own their claimed environments.
5. The Timer case lacks the explicit same-thread owner/reactor needed for its observable result.
6. Provider provenance is central to Detached but lacks a direct service-bound counterexample.

### Editorial improvements

- Clarify static selection versus purpose-bound metadata dispatch.
- Make the Coroutine result test its yielded values.
- Rename the partial implementation witness.
- State Wake's representation necessity conditionally on selecting push readiness.

### OpenSpec realization questions

- Preserve one execution-relative stack/growth/logical-depth context and verify two executions in
  non-LIFO alternation; current evaluator, native, and Wasm global/LIFO state is not evidence that
  independent ownership already exists.
- Derive exact dormant destroy per saved state and recursive Detached facts over executable
  environments and owned-provider captures.
- Preserve observable wake ordering and reclamation while allowing fused internal state tags.
- An execution Layout may omit an eager first continuation segment when the target can allocate it
  lazily under the selected fatal post-construction growth policy.

### Reviewer disagreements

The scope and simplification lenses treated each capability axis as independently outcome-capable;
the compiler lens found a strict surface reduction that preserves all three selected guarantees.
The examples lens did not challenge the selected guarantees but found invalid source witnesses.
Whether the axes require child SLPs or one explicitly bundled execution-admission thesis remains a
cohesion obligation for revision, not a vote on the author's already selected capability point.
