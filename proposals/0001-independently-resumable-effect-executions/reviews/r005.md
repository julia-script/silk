## Scope and language coherence

### Findings

The core owner-neutral execution and park/wake thesis remains cohesive, but five boundaries were
still either incomplete or over-selected.

1. Root parking relied on an implicit target owner absent from the representation matrix, while the
   text deferred enough of that owner that `rootTimer` had no complete execution contract.
2. The proposal rejected loans crossing construction and `onReady` but never selected whether a loan
   created inside an execution may remain live across external parking.
3. Fatal policy covered not only later continuation-stack growth but also initial erased body and
   callback packaging, hiding allocation that an explicit execution owner could recover from.
4. Wake minimality was described as following “accepted Silk,” although [generics, interfaces, and specialization](../../../docs/language/generics-interfaces-and-specialization.md) remains Candidate
   and the two narrow sealed erasures are themselves an extension of its static representation model.
5. Witness-specific resultless-spawn and join-allocation choices had leaked into substrate-level
   falsifiers despite canonical concurrency policy being a non-goal.

### Proposed split, if any

The root objection can be resolved without splitting only by selecting a complete synchronous target
entry delimiter here: target-owned root resources, drive/retain/wait-or-poll/redrive, no inline
resume, exact cleanup, final synchronous return, and target rejection when unavailable. Asynchronous
return-before-completion remains a dependent host proposal.

No storage-policy child is needed after separating caller-funded initial packaging from fatal later
stack growth. Canonical concurrency allocation remains a dependent library proposal.

## Examples and programmer model

### Findings

#### E1 — Nested joins exceed the one-slot queue witness

Two nested joins can park both a child and the root on the same empty ReadyInbox. Revision 21
reserved one ready-queue slot per task but no storage for multiple waiting Wake values. Therefore
`Scheduler.awaitReady` either allocated invisibly or could not represent the event order.

Required revision: in the direct witness, allocate one ReadyWaiter node before each `park`, carry
`! OutOfMemoryError ? &mut Allocator` through `awaitReady` and `Fiber.join`, and install the already
allocated node without allocating under shared access. A canonical Scheduler may later pre-reserve.

#### E2 — Ready-slot storage could not be reclaimed on completion

The completion callback captured TaskStore only, while ReadyInbox independently owned the reusable
slot. It could not release the idle slot. Revision 21 also lacked an explicit place for the retained
`onReady` environment's storage.

Required revision: each task reservation includes exact reusable readiness storage. ReadyInbox hands
that Allocation to `drive`; completion returns it to slot cleanup, readiness returns it through
`onReady`, and stale dequeue releases it. Completion captures a distinct ReadyInbox handle.

#### E3 — Root examples were not complete applications

`rootTimer` retained an open Timer requirement, so target validation could not yet know whether the
selected provider parks. The child example could also park its root while joining. A claim about
explicit construction on a target without root support additionally ignored the child's borrowed
Allocator requirement.

Required revision: show a complete EventedTimer provider application, validate root support after
specialization, add the target-root representation row, and stop using the open child as evidence
that an unsupported synchronous root can complete.

### Editorial corrections

- Replace obsolete `!E` generic binder syntax with ordinary type parameter `E`.
- Show `Deferred.await`'s exact `Shared.withMut` boundary and consume Wake afterward.
- Put the Coroutine pressure case in an Effect with visible allocation/failure rows.
- State that `TaskState.Parked` eligibility is represented by a dequeued identity, not the union tag.

## Compiler privilege and realizability

### Findings

#### C1 — Wake-cell reclamation missed transient runtime ownership

If Wake is consumed during registration and `onSuspend` then destroys Execution, the two stated
references can disappear before the callback returns even though the handshake still needs the
cell to suppress Latched notification. Reentrant destruction during `onReady` creates the analogous
notification hazard.

Required revision: Registering and Notifying operations transiently retain the cell. Detach
`onReady` before invocation. Reclaim only after Execution, Wake, and transient-operation ownership
are all gone. Name Registering, Latched, Dormant, Notifying, Eligible, and Cancelled states.

#### C2 — Initial erasure packaging was incorrectly fatal and hidden

Even a non-suspending Execution may need storage for erased `F` captures; the first park may need
storage for erased `R` captures. Those are fixed source-owned packaging costs, not dynamic recursive
continuation growth. Making both fatal undercut the explicit task-allocation witness and SLP-0002's
caller-funded pattern.

Required revision: expose exact `executionLayout<F>` and `readyLayout<R>`, initialize Execution from
caller-owned Allocation, and pass caller-owned readiness Allocation into drive. Safe wrappers use
ordinary Allocator/OutOfMemoryError without compiler recognition. Preserve fatal policy only for
later dynamic execution-stack growth.

#### C3 — Internal loans across parking were undecided

An owned Buffer can create a view after first drive and keep it live across park. [Effect suspension](../../../docs/language/effect-suspension.md) already
permits stable logical borrows across nested suspension; external parking must either preserve or
reject them.

Required revision: permit execution-internal loans whose referents are owned in the same Execution,
require relocation stability and borrow-before-owner cleanup, and reject loans into another
execution or across the construction/owner boundary. Keep Execution and Wake non-transferable until
parallel transfer rules exist.

### Smaller boundary, if any

Opaque Wake remains smaller than general callable erasure under [generics, interfaces, and specialization](../../../docs/language/generics-interfaces-and-specialization.md)'s selected direction. The
new Layout/Allocation operations are required to keep fixed erasure packaging explicit without
making Allocator compiler-known. An execution-step sum, explicit destroy, Scheduler token, or public
continuation remains unnecessary.

## Synthesis

### Proposal-level blockers

1. **Initial packaging allocation:** erased body and `onReady` storage were hidden fatal costs.
2. **Wake-cell lifetime:** required early-wake and reentrant-notification orders could reclaim active
   runtime state.
3. **Root delimiter:** ordinary root parking had no complete selected owner or representation tier.
4. **Internal loans:** external parking had no borrow rule for values created after construction.
5. **Nested waiter storage:** allocation-free join was false for simultaneous ReadyInbox waiters.
6. **Scope leakage:** witness-specific allocation policy had become substrate acceptance criteria.

### Editorial improvements

- Correct generic binder, Deferred access, Coroutine rows, and Parked eligibility examples.
- Make split metadata point back to SLP-0002.
- Block acceptance on both [generics, interfaces, and specialization](../../../docs/language/generics-interfaces-and-specialization.md)'s representation direction and SLP-0002.
- State that onSuspend denotes external park, not nested Effect.suspend.

### OpenSpec realization questions

- Lower caller-funded execution/readiness packages and prove every return/release path.
- Implement the complete execution and wake-cell state machines, including transient retains.
- Preserve stable internal loans and execution-local evaluator depth across drive and park.
- Validate complete specialized root entries against target-owner support.
- Exercise multiple nested join waiters, completion slot release, stale tombstones, and callback
  package reuse.

### Reviewer disagreements

The scope lens preferred splitting root ownership; the examples and compiler lenses allowed it to
remain if a complete synchronous entry delimiter and matrix row were selected. The synthesis keeps
that minimal synchronous root contract and continues to delegate asynchronous embedding. The scope
lens also preferred splitting storage procurement; the compiler lens supplied a smaller resolution:
caller-fund fixed erasure packages and retain fatal policy only for later dynamic stack growth.
