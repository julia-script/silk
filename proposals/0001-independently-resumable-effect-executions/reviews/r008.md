## Scope and language coherence

### Findings

#### S1 — A smaller eager-start, owner-sweep model satisfies the basic local-fiber cases

Revision 24 selects three capabilities together:

1. package a heterogeneous exact Effect before it begins, so its owner chooses first activation;
2. publish one task's readiness actively through retained `onReady`, enabling selective O(1) queues;
3. procure fixed execution and readiness packages through caller-funded Allocation, making package
   failure recoverable before insertion.

The scope and dedicated simplification lenses found that none is strictly necessary for functional
single-threaded fibers or event waits. A smaller model can run exact `F` immediately to completion or
first relinquishment, store only an actually relinquished continuation, legally recheck dormant
executions in owner sweeps, and use the existing fatal compiler execution-stack policy for retained
continuation storage.

That model genuinely loses deferred heterogeneous first activation, selective push readiness, and
recoverable package-allocation failure. Whether those are essential to the intended Scheduler and
future-parallel direction is an author value decision, not a fact autonomous review can settle.

#### S2 — Initial Execution is separable even though Revision 24 defends its utility

The new marker example proves that Initial Execution has observable independent semantics: the body
does not begin before owner-selected drive, and dropping it runs never-started environment cleanup.
An eager-start substrate cannot provide that behavior. The revision's argument establishes why the
capability is useful, but not that it is logically inseparable from parked-continuation ownership.

Smaller split: SLP-0001 could own exact start, relinquishment, dormant Execution, later drive, and
destroy; a dependent task-start proposal could add heterogeneous never-started packaging. Keeping
the current combined thesis is also coherent if deferred first activation is explicitly selected as
part of “scheduler authority,” not claimed to follow necessarily from parking.

#### S3 — “Source-defined fibers” needs a compositional qualification

The Shared-only witness rejects a child that joins another Fiber because moving the same
LocalScheduler into a task it owns creates a strong cycle. Weak ownership, scoped children, or a
cycle-safe child scheduling capability can change the admission/provider model and is not supplied
by current dependencies.

Required revision under either substrate choice: narrow the sufficiency claim to leaf tasks and
event waits under an explicit owner, or name the dependent concurrency capability that gates
compositional/nested fibers. Do not present this only as future naming, fairness, or API polish.

### Proposed split, if any

The smallest split is parked execution versus heterogeneous deferred first activation. The stronger
subtractive alternative removes both deferred start and push readiness in one smaller substrate.

## Examples and programmer model

### Findings

#### E1 — The primary Deferred `main` still crosses SLP-0003 statically

Although its concrete queue order never reaches `Scheduler.awaitReady`, `program` statically reaches
`Fiber.join -> Scheduler.awaitReady -> Intrinsic.park`. Exact conservative reachability therefore
makes the directly run complete entry park-capable. After the root split, that entry has no lifecycle
under SLP-0001 alone.

Required revision: close and reify `program`, wrap it in an explicit outer Execution owned by a
source driver, or mark the example dependent on SLP-0003. Add the case where Scheduler and Allocator
are satisfied but the complete park-capable entry still lacks an owner.

#### E2 — Timer outer construction fails to reify typed failure

`concurrentTimer` may fail with `TimerError | OutOfMemoryError`, but
`prepareConcurrentTimer` passes it directly to `Execution.make`, whose `F` contract is infallible.

Required revision: close providers, apply `Effect.result`, and construct
`Execution<Result<i32, TimerError | OutOfMemoryError>>`. The source driver observes Success(42) or
ordinary reified failure data; outer package allocation retains its separate OutOfMemoryError.

#### E3 — The Initial-state example is incomplete and ill-typed

It enqueues `Execution<i32>` into a Scheduler operation accepting `Execution<()>`, leaves
`reservation` undeclared, omits allocation and requirement rows, and never actually reads the Shared
marker. It also fails to state that enqueue publishes an initial ReadyTask identity and readiness
Allocation, which `driveOne` requires before selecting the task.

Required revision: make the child return unit, put the example in a complete Effect with Scheduler
and Allocator rows, reserve before construction, read the marker before and after drive through a
named callback, and specify atomic publication of task state plus initial ready identity/storage.

#### E4 — `typeof(probe)` invents local value reflection

Current `typeof(item)` names a visible specialized function item; it does not reflect the hidden
representation of an opaque local callback binding.

Required revision: define a generic helper whose `&R` value parameter infers the opaque callback
representation and whose body calls `Intrinsic.readyLayout<R>()`. Query with `&probe`, then drop the
probe. Do not generalize `typeof`.

## Compiler privilege and realizability

### Findings

#### C1 — Smallest complete counterproposal

```silk,ignore
Intrinsic.Execution<A>
Intrinsic.Detached

effect fn Intrinsic.start<
  A,
  B,
  F: once Effect<A> + Intrinsic.Detached,
  C: once fn(A) -> B,
  S: once fn(Intrinsic.Execution<A>) -> B
>(body: F, onComplete: C, onRelinquish: S) -> B

effect fn Intrinsic.drive<
  A,
  B,
  C: once fn(A) -> B,
  S: once fn(Intrinsic.Execution<A>) -> B
>(execution: Intrinsic.Execution<A>, onComplete: C, onRelinquish: S) -> B

effect fn Intrinsic.relinquish<G>(guard: G) -> G
```

`relinquish` retains `G` in compiler-derived continuation state. Redriving a relinquished execution
is legal: it resumes, rechecks durable source state, and may relinquish again. A scheduler drives each
dormant task at most once per round and begins a new round after another task step or a same-thread
reactor event. No busy wait is required.

This removes opaque Wake, `wake`, both Layout operations, `executionFromAllocation`, readiness
Allocation, retained `R`, its Detached erasure, eligibility states, Dormant-drive trap, and ready-
queue tombstones. Continuation exhaustion remains fatal like [Effect suspension](../../../docs/language/effect-suspension.md).

| Functional local Fiber/Deferred progress | yes | yes |
| Same-thread evented waits | push Wake | reactor event plus owner sweep |
| Ordinary Effects hide Pending | yes | yes |

### OpenSpec realization requirements if Revision 24 is retained

- Represent stack/segment root, growth and logical-depth state per Execution; alternate two explicit
  executions non-LIFO while preserving the cheap nested-only path.
- Generate a distinct dormant-destroy plan per saved park state, cancelling Wake before ending loans
  and cleaning affine owners/guards.
- Derive Detached recursively from exact executable environments and owned-provider captures rather
  than stored-representation admission or Effect result types.

## Synthesis

### Proposal-level blockers

1. **Author capability decision:** retain deferred start, push readiness, and recoverable explicit
   packaging, or adopt the smaller eager-start owner-sweep substrate.
2. The primary Deferred example and Timer example still violate their Execution/failure boundaries.
3. The new Initial-state example and readiness-layout query are not valid complete Silk witnesses.
4. Fiber sufficiency overstates composition available without a cycle-safe child capability.

### Editorial improvements

Add owner-sweep relinquishment as the strongest smaller alternative even if Revision 24 is retained;
the existing alternatives consider only public Pending and a bare separately registered park.

### OpenSpec realization questions

Execution-relative contexts, state-specific dormant destroy, and recursive Detached derivation remain
OpenSpec work only if the richer Revision 24 model survives the proposal decision.

### Reviewer disagreements

The examples and compiler lenses focused on correcting the selected model. The scope and dedicated
simplification lenses independently found deferred first activation separable; the simplification
lens additionally showed that active Wake notification and caller-funded packages can be removed by
accepting owner sweeps and fatal runtime exhaustion. No reviewer established that one capability
bundle dominates for all author priorities.

## Revision response

Resolved in Candidate revision 25 after the author selected the recommended richer substrate:

1. Retained Initial Execution, push Wake readiness, and caller-funded execution/readiness packages.
   Reframed the surface as minimal for owner-controlled first activation, O(1) task-specific
   readiness, and recoverable fixed-package procurement rather than the absolute smallest way to
   make local tasks progress. Added the three-operation eager-start owner-sweep model as the strongest
   rejected alternative with its exact capability losses.
2. Closed Scheduler and Allocator providers around the primary Deferred program, reified its typed
   allocation failure, and constructed an explicit outer
   `Execution<Result<i32, OutOfMemoryError>>`. Its direct complete-entry form is now rejected for
   park capability without an owner even when all service requirements are satisfied.
3. Reified Timer/allocation failure before outer Timer execution construction and changed the source
   driver contract to `Execution<Result<i32, TimerError | OutOfMemoryError>>`.
4. Replaced the fragmentary Initial-state example with a complete unit child carrying exact failure
   and requirement rows, explicit reservation, pre/post Shared reads, and the atomic initial
   TaskReady/ReadyTask/readiness publication event.
5. Replaced invalid `typeof(probe)` reflection with a generic `readinessLayoutFor(&R)` helper whose
   value argument infers the opaque callback representation.
6. Narrowed the proven source sufficiency claim to closed leaf tasks, Deferred coordination, and
   event waits under an explicit owner. Nested/provider-inheriting fibers remain a dependent
   concurrency design rather than an unearned substrate claim.
