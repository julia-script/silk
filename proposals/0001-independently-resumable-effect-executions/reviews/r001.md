## Scope and language coherence

### Findings

The central thesis is cohesive: independent execution ownership and race-free parking are the two
missing control powers required for ordinary-source fibers. A bare park without an owned execution
cannot give source code dormant lifecycle authority, while an execution that can only be stepped to
completion cannot wait for external readiness. Canonical scheduling, structured concurrency,
parallel execution, timers, and public Coroutine typing remain valid dependent proposals.

Two edges are not yet bounded tightly enough:

1. Root browser-host completion is source-observable, not merely a backend storage choice. After a
   Wasm export returns control to JavaScript, the proposal does not say how the eventual `A`, typed
   failure, or fatal report reaches the embedding. The `rootTimer() -> i32` case therefore cannot yet
   have the claimed observable result on every named target.
2. Source-state allocation is presented as deferred library policy, but the Scheduler-only driving
   API and the supposedly complete witness make incompatible assumptions about it. That choice may
   remain outside the compiler substrate, but one complete witness must select one path.

### Proposed split, if any

No split of execution from parking is recommended. Browser embedding could become a dependent host
proposal, but this Candidate must then narrow the root-browser claim and stop using it as completed
evidence. Alternatively, it can state the minimal generic host completion contract here without
selecting a JavaScript Promise or canonical library API.

## Examples and programmer model

### Findings

The direct, nested, and independently resumable tiers are clearly distinguished. The examples also
successfully prevent “owner-selected order” from being misread as arbitrary frame execution.

Four concrete counterexamples expose missing contracts.

#### E1 — Scheduler-only requirements are not demonstrated

The driving program declares only `? &Scheduler`, and the witness gives `Fiber.fork` the same public
requirement. Its body calls `Deferred.make`, whose SLP-0002 construction path requires
`! OutOfMemoryError ? &mut Allocator`. The prose says storage “may” use a pre-reserved Scheduler arena
or expose allocation channels, but neither path is written through end to end. The first changes
Scheduler construction, capacity, and exhaustion policy; the second changes the displayed Effect
rows. The witness is therefore conditional rather than complete.

Required revision: select one non-normative but internally complete storage policy. Either show the
Allocator and failure rows honestly throughout, or show how Scheduler construction reserves source
storage and how `Deferred.make`/`Fiber.fork` consume it, including capacity exhaustion. The compiler
surface need not change.

#### E2 — A stored wake may outlive the execution

The selected signature admits this shape:

```silk,ignore
let leaked = run Shared.make(WakeSlot.empty())

run Intrinsic.park(fn(wake) {
  WakeSlot.put(&leaked, move wake)
  return () // G is unit and owns no unlink action
})
```

The owner can later drop the suspended `Execution` while `leaked` still owns the readiness callback.
Invoking that callback must not dereference freed frame or execution state. The proposal repeatedly
attributes safety to dropping `G`, but the generic signature does not require `G` to own, find, or
unlink every stored copy of the one-shot callback.

Required revision: select a sound lifetime contract. The smallest callback-preserving option is for
the callback to own a stable compiler/runtime park cell distinct from continuation frames. Dropping
the execution marks the cell canceled and releases its side; invoking a retained callback afterward
is a defined no-op or fatal misuse without touching freed storage, and dropping the callback releases
its side. A larger alternative is a typed paired wake/guard capability whose lifetime relationship
the compiler can enforce. Merely documenting that ordinary `G` unregisters is insufficient.

#### E3 — Stale ready identities contradict the witness code

The wake table says that dropping an eligible execution may leave a stale queue identity that the
Scheduler discards. `Scheduler.driveOne`, however, treats `TaskStore.takeReady(id)` as returning an
`Execution<()>` unconditionally. This is an editorial inconsistency, not a primitive blocker:
`takeReady` should return an option/result and the loop should discard stale identities.

#### E4 — Root browser completion is incomplete

The event-order prose ends with a later host drive, but does not show who owns the root between JS
turns or how completion of `rootTimer() -> i32` is observed. A synchronous Wasm export cannot return
that `i32` after it has already yielded to the event loop.

Required revision: provide a minimal host-boundary case for completion, typed failure, and dormant
root destruction, or explicitly remove browser-root completion from this SLP's claimed evidence and
delegate it to a named dependent proposal.

### Missing or corrected cases

- Add drop-before-first-drive cleanup; a freshly constructed `Execution` owns the Effect body and
  its captures even before any suspension occurs.
- State that `onReady` cannot run until the complete `onSuspend` callback invocation returns, not
  merely after that callback receives the execution argument.
- Correct `driveOne` to tolerate a stale source identity.
- Add the retained-wake-after-execution-drop counterexample and its selected behavior.
- Show one exact source allocation path through the Scheduler/Fiber/Deferred witness.

## Compiler privilege and realizability

### Findings

#### C1 — `Execution<A>` erases capture provenance without a selected safety model

Silk's existing callable and Effect representation parameters preserve exact construction,
captures, layout, cleanup, and static target. Distinct representations do not implicitly erase into
one runtime container. The Candidate instead places arbitrary children into homogeneous
`Execution<()>` storage while `Execution<A>` exposes neither a representation parameter, requirement
row, nor capture region.

This is not only a layout question. An execution may retain `&Logger`, `&Scheduler`, or another
borrowed provider. After that value is inserted into a dynamic TaskStore, the compiler must still
prevent the referent from moving or dropping until the execution is removed and completed or
destroyed. Per-value hidden loan facts are not obviously preserved through a homogeneous dynamic
collection, and an execution borrowing the Scheduler provider can be stored indirectly in the same
Scheduler whose lifetime it constrains.

Required revision: select one coherent model and pressure it through insertion, removal, dormant
drop, and provider-scope exit. Plausible models include:

- a compiler-visible capture/region parameter on `Execution`, plus an explicit type-erasure owner
  whose restrictions are stated;
- restricting detached executions to owned/non-borrowing captures and providing shareable owned
  service handles before construction; or
- a scoped execution/task-store type that conservatively carries all retained loans and proves they
  end before provider teardown.

Calling the facts “the same as any stored Effect or callable” does not settle the issue because those
types currently preserve exact representation parameters rather than erasing them.

#### C2 — Callback-shaped wake needs runtime ownership beyond `G`

The E2 counterexample is also a compiler-boundary issue. If the callback directly references
execution storage, the selected surface is unsound. A stable park cell can preserve the public
callback surface, but it becomes part of the semantic execution lifecycle and pay-for-use analysis:
who owns it, when cancellation becomes visible, how local reference ownership is counted, and what a
later cross-thread realization must atomically preserve.

The callback API can remain the smallest surface only after that hidden ownership is selected. If
the language instead needs a typed wake/guard relation, the current subtraction of a Wake type must
be revisited.

The current compiler already has suspension-frame planning, resume dispatch, cleanup plans, and
callable capture facts, so reusing the continuation foundation is credible. The missing evidence is
at the new erasure and independent-lifetime seams, not in basic coroutine construction.

### Smaller boundary, if any

No strictly smaller sound boundary was found. A bare park loses lifecycle authority and registration
atomicity; a callback-only continuation cannot be stored or destroyed; compiler-known Fiber or
Deferred policy is larger. The selected callbacks may remain minimal if a stable canceled park cell
and a sound capture-erasure/scoping model can be specified without adding source operations.

## Synthesis

### Proposal-level blockers

1. **Execution capture and provider provenance:** homogeneous `Execution<()>` storage lacks a
   selected model that preserves borrowed captures and provider teardown safety.
2. **Retained wake lifetime:** the generic `G` contract does not prevent a stored readiness callback
   from outliving a dropped execution; hidden stable ownership or a larger typed surface is required.
3. **Source-sufficiency allocation path:** the Scheduler-only examples and SLP-0002 allocation rows
   are not joined by one complete ordinary-source implementation path.
4. **Root browser completion:** eventual success/failure delivery and root destruction after yielding
   to the host event loop remain undefined.

Each finding can be resolved without abandoning owner-neutral independently resumable executions,
but each may change the type surface, runtime lifecycle, or claimed programmer model and therefore
requires a new Candidate revision.

### Editorial improvements

- Make `TaskStore.takeReady` explicitly fallible for stale source identities.
- Add fresh-execution drop to the cleanup cases.
- Replace “onSuspend receives ownership” with “the onSuspend invocation returns after transferring
  ownership” wherever that stronger ordering is intended.
- Distinguish cancellation safety from source-level unlink efficiency: a guard may remove a waiter,
  but memory safety cannot depend on arbitrary source code doing so correctly.

### OpenSpec realization questions

- Define the independent execution state machine and illegal transition diagnostics once the two
  ownership blockers are resolved.
- Map direct, nested-only, and external-wake reachability to evaluator, native, and Wasm artifacts.
- Specify frame cleanup tables for never-driven, running-to-completion, dormant-drop, ready-drop, and
  fatal states.
- Define host adapter scheduling hooks and target-specific storage after the source-observable root
  completion contract is selected.
- Prove that no Scheduler, Fiber, Deferred, timer, Coroutine, or Allocator actor is recognized by
  spelling.

### Reviewer disagreements

The scope lens preferred delegating browser embedding to a separate host proposal. The examples lens
objected that `rootTimer` currently uses browser completion as central evidence, so delegation is
valid only if this Candidate narrows that claim. The realizability lens considered the callback
surface salvageable through a hidden stable park cell, while the scope lens noted that a typed Wake
may still be necessary if Silk refuses runtime-owned cancellation state. All lenses agree that the
current text has not selected either model.

## Revision response

Resolved in Candidate revisions 16–20:

1. **Execution capture and provider provenance (C1):** revision 16 restricts
   `Intrinsic.execution` to a closed Effect whose exact representation retains no lexical value or
   provider loan. Owned provider values are moved into the Effect before representation erasure.
   Revision 20 keeps the illustrative child Effect closed and uses Scheduler only while inserting
   the task, rather than designing automatic provider inheritance or introducing a
   `TaskStore -> Execution -> Scheduler -> TaskStore` ownership cycle. Arbitrary borrowed child
   environments remain delegated to a scoped-fiber proposal.
2. **Retained wake lifetime (E2/C2):** revision 17 selects a hidden stable wake-control cell shared
   by execution and callback. Execution destruction cancels it before frame cleanup and releases
   `onReady`; a retained late callback is a safe no-op. `G` is prompt unlink/resource policy and is
   not trusted for memory safety.
3. **Source-sufficiency allocation path (E1):** revision 18 selects direct pay-as-needed source
   allocation. Scheduler, Deferred, task, and join-result construction expose
   `? &mut Allocator ! OutOfMemoryError`; resultless infallible spawn omits result state, and task
   construction reserves reusable ready-link storage so notification and join do not allocate.
4. **Browser-root completion (E4):** revision 19 removes asynchronous browser embedding from scope
   and narrows the evidence. Park-capable roots require a compatible target owner; browser Promise,
   callback, eventual outcome delivery, cancellation, and exported ABI belong to a separate host-
   integration proposal. Targets without that contract reject park-capable synchronous exports.

Revision 20 also completes the editorial requests: `TaskStore.takeReady` returns an option and stale
identities are discarded; dropping a freshly constructed never-driven execution cleans its body and
captures exactly once; the complete `onSuspend` callback returns before `onReady`; and source guard
cleanup is explicitly separated from runtime cancellation safety.
